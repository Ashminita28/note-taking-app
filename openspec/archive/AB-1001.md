## 7. Open Questions

1. **shadcn/ui component set:** FRS/SDS don't specify which shadcn/ui primitives to pre-install at
   setup time vs. adding them incrementally as each frontend ticket needs them. Recommend
   installing only the `shadcn/ui` CLI + theme config now, adding components on demand per ticket.
2. **Playwright scope for AB-1001:** SDS doesn't specify browser targets or base URL config for the
   initial Playwright setup. Recommend a minimal single-project (Chromium) config with
   `baseURL` pointed at the Vite dev server, to be expanded when AB-1016 (E2E Journey) needs it.
3. **`.env.example` values:** Should defaults in `.env.example` mirror the SDS §7.2 table exactly
   (e.g. `BCRYPT_ROUNDS=12`, `JWT_ACCESS_EXPIRY=15m`), including for variables marked "Required:
   Yes" with no default (`DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGIN`)? Recommend documenting them
   as placeholders (e.g. `JWT_SECRET=changeme`) with a comment, since Zod validation only checks
   presence, not value quality, at this stage.
4. **Test placeholder strategy:** AC #4 requires `pnpm test` to pass "with no test files or
   placeholder tests." Recommend one trivial placeholder test per workspace package (backend,
   frontend, shared) so Vitest doesn't error on zero test files, rather than relying on Vitest's
   `passWithNoTests` flag — keeps CI behavior explicit either way; needs a decision before `/plan`.

> **Resolution adopted for planning purposes:** all four recommendations above are adopted as
> stated (shadcn/ui CLI + theme only; minimal Chromium Playwright config; placeholder `.env.example`
> values with comments; one trivial placeholder test per package). Revisit if the user overrides
> during `/tasks` or `/implement`.

> **Implementation-time deviation (discovered during `/implement`):** ESLint 9.25.0 (pinned per SDS
> §3.1.4) defaults to flat config and will not auto-load `.eslintrc.cjs` (the filename SDS §5
> explicitly specifies) without `ESLINT_USE_FLAT_CONFIG=false` set at invocation. Setting that env
> var inline in a `package.json` script is not portable to Windows `cmd.exe` without a helper, so
> `cross-env` (`7.0.3`) was added as a root devDependency beyond SDS §3.1.4's literal list, and each
> package's `lint` script was changed to `cross-env ESLINT_USE_FLAT_CONFIG=false eslint src/`. This
> is the smallest change that keeps the SDS-mandated `.eslintrc.cjs` filename working with the
> SDS-pinned ESLint version.

> **Implementation-time deviations (discovered during `/implement`), beyond the ESLint one already
> noted above:**
> 1. **`packages/shared` module resolution.** The barrel (`src/index.ts`) originally re-exported
>    without file extensions (`export * from './constants/errors'`), which works under Vite/Vitest's
>    bundler-style resolution but silently drops every re-export when a `NodeNext`-resolving
>    consumer (the backend) reads the compiled `.d.ts`/`.js` — and would fail outright under Node's
>    own ESM loader at runtime. Fixed by compiling `packages/shared` with `NodeNext` module settings
>    and adding explicit `.js` extensions to the barrel's relative exports.
> 2. **Docker port conflict.** Host port 5432 was already bound by an unrelated project's Postgres
>    container on this machine; remapped to `5433` in `docker-compose.yml`, `.env.example`, and
>    `apps/backend/vitest.config.ts`.
> 3. **`@vitest/coverage-v8` added** (pinned to the same `3.2.1` as `vitest`) to all three packages —
>    SDS §3.1.1–3.1.2's manifests list `vitest` but not its coverage provider, which every
>    `test:coverage` script requires.
> 4. **Coverage scoping.** Each `vitest.config.ts` sets `coverage.include: ['src/**']` (otherwise
>    `dist/`, `vitest.config.ts` itself, and — for frontend — the built asset bundle count as 0%
>    against the total) and excludes genuinely non-unit-testable files: build entrypoints
>    (`server.ts`, `main.tsx`), pure route wiring (`App.tsx`, covered instead by the Playwright
>    smoke test), and the single-heading placeholder pages under `src/pages/` that AB-1010–AB-1015
>    will fully rewrite.
> 5. **`apps/frontend/src/lib/utils.ts`** (the shadcn `cn()` helper) was added alongside
>    `components.json` — not separately itemized in the Plan, but required by `components.json`'s
>    own `aliases.utils` path and by every future shadcn component.
> 6. **`rate-limiter.ts` refactor.** Extracted the 429 handler into an exported `rateLimitHandler`
>    function so it's unit-testable in isolation, instead of only reachable by tripping the real
>    100-request rate limit.
